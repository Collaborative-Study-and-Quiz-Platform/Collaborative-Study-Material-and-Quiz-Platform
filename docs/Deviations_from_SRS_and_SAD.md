# Deviations from the SRS, SAD and Test Plan

**Project:** Collaborative Study Material and Quiz Platform (CSQP), Team 13
**Course:** UE24CS341A Software Engineering
**Applies to:** SRS v1.0, SAD v1.0, Test Plan v1.0, compared with the code frozen at the end of Sprint 2

Agile development let the design change as we built it. Each change below is listed with what the document said, what we built, and why.

| # | Area | Document said | What we built | Reason | Impact |
|---|---|---|---|---|---|
| D-01 | Analytics integration (SAD component view, CSQP-F-040, F-041, F-042) | The Node.js backend sends attempt data to the Python analytics microservice, and the dashboard shows the report it returns. | The analytics microservice is built and tested on its own (`analytics-service/`, endpoints `POST /analytics/individual` and `POST /analytics/class`). The dashboard renders reports with the same structure from a fixed seeded dataset (`frontend/src/analytics/seedData.js`). The backend does not call the service yet. | Sprint 2 time went to quiz, grading and question bank features with higher priority. SRS AC-042 asks for charts on a seeded dataset, so the dashboard meets its acceptance criterion. | Live analytics needs one backend call to the service. Planned as the next increment. |
| D-02 | Charts library (CSQP-F-042) | Recharts or Chart.js on the React frontend. | Custom SVG charts in `frontend/src/analytics/Charts.jsx`, each with a matching data table. | No extra dependency, full control over accessibility (every chart also has a table, CSQP-NF-004). | None for the user. |
| D-03 | File storage (SAD technology stack) | Cloud object storage or MongoDB GridFS. | Local disk storage in `backend/uploads/materials`, path set by `MATERIAL_UPLOAD_DIR`. | No external accounts needed for the demo. Storage is isolated in `materialStorage.js` so it can be swapped later. Path traversal, symlink and directory attacks are covered by tests. | Must move to cloud storage before multi-server deployment. |
| D-04 | Registration security (SAD STRIDE, Spoofing) | Email verification on registration. | Registration sends a welcome email and an in-app notification. No verification link step. | Kept registration simple within the sprint. Spoofing is handled by signed JWTs, bcrypt and rate limiting. | Low. Can be added on top of the existing email service. |
| D-05 | Logging (SAD operations) | Structured logging, for example Winston. | Health and readiness endpoints (`/api/health`, `/api/health/ready`) and an uptime monitor that writes JSON lines (`npm run uptime:monitor`). | Covers CSQP-NF-003 (availability) directly without a logging framework. | Low. |
| D-06 | Load test tool (CSQP-NF-001, NF-002, Test Plan section 6) | JMeter or k6. | A Node.js load runner in `backend/loadtest/` (`npm run loadtest`) with 100 virtual users. | Runs in the same toolchain as the tests, no extra install. | None. |
| D-07 | Login performance finding (CSQP-NF-001) | p90 response time at most 2 s. | With Node's default 4-thread pool, bcrypt (cost 12, required by CSQP-SR-002) made login p90 exceed 2 s under load. With `UV_THREADPOOL_SIZE=8` it passes. | Security requirement SR-002 and performance requirement NF-001 compete. We kept bcrypt cost 12 and tuned the thread pool. | Deployment must set `UV_THREADPOOL_SIZE=8`. Documented in `backend/loadtest/README.md`. |
| D-08 | Security scan (CSQP-SR-005) | OWASP ZAP automated scan. | Automated tests for Mongo operator injection, HTML/script payloads, input validation and auth rate limiting (`backend/test/sprint2-security.test.js`, `material-comment-rate-limit.test.js`). | Tests run on every pull request in CI, unlike a one-off scan. | ZAP scan can be added as an extra check. |
| D-09 | Test cases (Test Plan section 15) | 12 representative test cases. | Expanded to the full list in `docs/testing/Updated_Test_Cases.md` (TC-Auth-04, TC-Mat-02 to 05, TC-Quiz-02 and 04 to 07, TC-QB-02 to 04, TC-Perf-02 to 04, TC-Collab-01 to 03, TC-Sec-01 to 05). | The Test Plan said the set would be expanded during execution. | Traceability is complete for every FR and SR. |
| D-10 | CI pipeline (CSQP-NF-005) | Build, lint and test before merge with 70% coverage. | GitHub Actions (`.github/workflows/ci.yml`) runs backend tests with a c8 gate of 70% for lines, statements, functions and branches, plus frontend lint and build and the analytics service tests, on every pull request to `main`. | As planned. The gate covers the backend, where the business and security logic is. | Frontend coverage is reported but not gated. |
| D-11 | Load test after Sprint 2 security changes (CSQP-NF-001, NF-002, SR-005) | Load test logs in 100 virtual users as one test account. | Sprint 2 added password hashing in the User model and a login rate limit of 15 attempts per 15 minutes per client (SR-005). The load script pre-hashed the password (so it was hashed twice and login failed with 401) and sent every login from one address (so the limiter returned 429). The script now lets the model hash the password and gives each virtual user its own client address. | Re-running the load test after the security changes found these regressions, as regression testing in the Test Plan intends. | Finding for deployment: students behind one shared campus network address share one login limit, so the limit should be tuned per user as well as per address. |

## Requirements that stayed as written

All other functional requirements (CSQP-F-001 to F-033, F-043, F-050 to F-052), non-functional requirements and security requirements (CSQP-SR-001 to SR-005) were implemented as specified. The architecture pattern (a layered modular monolith with one Python analytics microservice) is unchanged.
